# Amazon S3

The S3 driver stores files in an Amazon S3 bucket, or in any store that speaks the S3 API (Cloudflare R2, Backblaze B2, Wasabi, DigitalOcean Spaces, SeaweedFS, Garage, MinIO). It is the backend with the most capabilities: server-side copy, batch deletes, SigV4 signed URLs, multipart uploads, and presigned parts that let a browser upload a large file straight to the bucket in pieces.

This page covers AWS itself and everything the driver does. [S3-compatible stores](s3-compatible.md) gives a ready DSN and the known differences for each other provider.

## Before you start

- The package is `github.com/ubgo/filesystem/adapters/s3`, a module of its own built on `aws-sdk-go-v2`. Its reference is [adapters/s3/README.md](../../adapters/s3/README.md).
- The runnable program is [`examples/adapters-s3`](../../examples/adapters-s3/). It runs every snippet on this page against an in-process fake S3 ([gofakes3](https://github.com/johannesboyne/gofakes3)), so `go run ./adapters-s3` from `examples/` needs no account. The same program also passes against a local SeaweedFS.
- You need a bucket and credentials that may read, write, list and delete in it. The driver never creates buckets.

## 1. Install

```sh
go get github.com/ubgo/filesystem github.com/ubgo/filesystem/adapters/s3
```

Uploads go through the SDK's `feature/s3/transfermanager`, the successor of the deprecated `feature/s3/manager`. A body of unknown length streams as a multipart upload; it is never buffered whole.

On AWS you would normally load the client with `config.LoadDefaultConfig(ctx, config.WithRegion("eu-west-1"))` and `s3.NewFromConfig(cfg)`, which reads credentials from the default chain (step 4).

Every `Config` field:

| Field | Default | What it does |
|---|---|---|
| `Client` | required | The `*s3.Client`. `New` returns `CodeInvalidArgument` without it. |
| `Bucket` | required | The bucket name. |
| `Visibility` | `VisibilityNone` | `VisibilityNone`: the bucket policy decides who reads; no ACL is sent and `SetVisibility` is not declared. `VisibilityACL`: per-object `public-read` / `private` canned ACLs. Any other value is `CodeInvalidArgument`. |
| `ConditionalWrites` | `false` | Declares that the provider honours `If-None-Match: *` on PUT, which turns on the `ConditionalWrite` capability. |
| `ServerSideEncryption` | empty | Sent on every write, copy and multipart upload, e.g. `"AES256"` or `"aws:kms"`. |
| `SSEKMSKeyID` | empty | The KMS key (ID, ARN or alias ARN) this disk encrypts with; needs `aws:kms` or `aws:kms:dsse`, and an empty `ServerSideEncryption` becomes `aws:kms`. Anything else is `CodeInvalidArgument`. |
| `SSEKMSKeyFor` | nil | `func(key string) string` picking the KMS key per object (per tenant prefix) on a disk shared by many tenants; `""` falls back to `SSEKMSKeyID`. Same rules as `SSEKMSKeyID`. See "One KMS key per tenant" below. |
| `StorageClass` | empty | Sent on every write, copy and multipart upload, e.g. `"STANDARD_IA"`. |
| `PartSize` | 0 (SDK default, 8 MiB) | Part size of uploads through the transfer manager. Negative is `CodeInvalidArgument`. |
| `Concurrency` | 0 (SDK default, 5) | Parts of one upload in flight at once. Raise it for throughput on a fast link; lower it on a small machine, since each part in flight holds `PartSize` bytes. Negative is `CodeInvalidArgument`. |
| `ExpectedBucketOwner` | empty | The 12-digit account ID that must own the bucket, sent on every request and signed into presigned URLs (see "Bring your own bucket"). |
| `RequestPayer` | empty | `requester` accepts a requester-pays bucket's charges on every request, signed into presigned URLs. |
| `PrivateACL` | `CannedPrivate` | The canned ACL `VisibilityACL` gives private objects, such as `CannedBucketOwnerFullControl` for writes into another account's bucket; public ACLs are `CodeInvalidArgument`. |
| `Clock` | `time.Now` | The time the driver dates from: `ObjectLockDays` retentions, the `MaxRetention` check, whether a retention still holds an object, and the signing time and `ExpiresAt` of presigned URLs, parts and forms. Pass a clock synchronised with S3 on a host whose clock drifts (SigV4 refuses requests more than 15 minutes off). Retry-After waits stay on the wall clock. |
| `PruneEmptyPrefixes` | `false` | A non-recursive List drops "directories" that hold no object, at one extra request per directory listed. For filer-backed stores such as SeaweedFS (step 9). |
| `SweepUploads` | `false` | Declares `SweepAbandoned` and its dry run `FindAbandoned`; the sweep aborts the bucket's multipart uploads initiated before a cutoff (see [multipart](#8-multipart-uploads-and-presigned-parts)). |
| `UnverifiedSignedHeaders` | `false` | Declares that the store does not verify SigV4 signatures, withdrawing `PresignHeaders` (see [signed URLs](#7-signed-urls)). |

Check: `disk.Capabilities()` prints `[copy,delete-prefix,delete-keys,presign,multipart,presign-part,presign-post,metadata,content-type,headers,presign-headers,checksum-sha256]` with the defaults.

Plus the Mux's own `prefix`, `public_url`, `visibility` and `readonly`, which work for every scheme (see [configuration](../concepts/configuration.md)).

Validation, all at open time and all `CodeInvalidArgument`:

- A DSN without a bucket (`s3://?region=x`).
- A parameter not in the table (`s3://b?nope=1`), so a typo fails at start-up.
- A boolean that `strconv.ParseBool` rejects (`path_style=maybe`), a `part_size`, `concurrency` or `object_lock_days` that is not an integer or is negative, an `expected_bucket_owner` that is not a 12-digit account ID, a `request_payer` other than `requester`, or an unknown `object_lock_mode`, `restore_tier` or `checksum`.
- `object_lock` or `versioning` on a bucket that does not have it (the opener asks the bucket), or an `sse_c_key_env` variable that does not hold a base64 32-byte key.
- An AWS config file the SDK cannot load, or a `profile` it does not contain.
- Credentials in the URL (`s3://key:secret@bucket`), `profile` together with a `*_env` parameter, only one of `access_key_env` and `secret_key_env`, or a named variable that is unset or empty. The error names the parameter or the variable, never a value.
- `role_arn` without `external_id` or `role_session_name`, a `role_duration` that is not a duration or is outside 15m to 12h, or `external_id`, `role_session_name` or `role_duration` without `role_arn`. A role STS refuses to let the application assume (wrong external ID, a trust policy that does not name the application's account) is `CodePermission`, also at open time, because the opener assumes the role once.

Opening sends no request unless `object_lock` or `versioning` is set, which costs one bucket request each: credentials are resolved on the first operation. Run `disk.Check(ctx)` at start-up to prove the bucket and credentials work (it writes, reads back and deletes a small object under `.filesystem-check/`).

### Server-side encryption per disk

S3 encrypts every object at rest. By default the bucket's own setting decides how (SSE-S3 on every bucket since 2023, or the bucket's default KMS key). Two disks on the same bucket, or one tenant's disk among many, can choose their own:

```text
s3://media?region=eu-west-1&sse=AES256
s3://tenant-a?region=eu-west-1&sse_kms_key_id=arn:aws:kms:eu-west-1:111122223333:key/1234abcd-12ab-34cd-56ef-1234567890ab
```

- `sse=AES256` is SSE-S3, with keys S3 manages. `sse=aws:kms` uses the AWS-managed KMS key unless `sse_kms_key_id` names one; `sse_kms_key_id` alone implies `aws:kms`. `aws:kms:dsse` (dual-layer) works the same way. A KMS key with `sse=AES256` is refused when the disk opens.
- The encryption goes on every request that creates data: `Write`, `Copy`, `CreateMultipart`, and the presigned PUT, which signs both headers so the client must send them unchanged (they are in `SignedRequest.Header`) and a direct upload is encrypted like any other.
- The writer needs `kms:GenerateDataKey` on the key and readers `kms:Decrypt`; a key the caller cannot use makes S3 refuse the write (`CodePermission`).
- A KMS key ID is not a secret (S3 returns it on every HEAD), so it is safe in a DSN. For keys the application holds itself (SSE-C), see step 14.
- The repository's tests check that each write path sends the headers (and the presigned PUT signs them); that S3 then encrypts with that key needs a real bucket and key. The example's `kmsKeyPerTenant` step (next section) shows a disk-wide `SSEKMSKeyID` on every write outside a tenant: `kms: shared/terms.txt -> aws:kms …/default-key`.

### One KMS key per tenant on a shared disk

When tenants share one bucket and one client, each under its own prefix (a scoped disk per tenant, see [Manager](../concepts/disks-and-drivers.md)), `Config.SSEKMSKeyFor` picks the key per object instead of per disk. It gets the key as the driver sees it, under the scope's prefix, and returns that tenant's key, or `""` for `SSEKMSKeyID` (or the bucket's default when that is empty too):

The example puts two tenants and a shared file on one disk, with a default key for keys outside any tenant, and prints the encryption headers each PUT carried (from the fake's request log):

```go
func kmsKeyPerTenant(ctx context.Context, out io.Writer, client *s3.Client, fake *fakeS3) error {
	keys := map[string]string{"acme": acmeKMSKey, "globex": globexKMSKey} // loaded at start-up
	disk, err := newBucketDisk(ctx, client, "app-files", fss3.Config{
		SSEKMSKeyID: defaultKMSKey, // the disk's key, for keys outside any tenant
		SSEKMSKeyFor: func(key string) string { // the key as the driver sees it, under the scope's prefix
			tenant, _, _ := strings.Cut(strings.TrimPrefix(key, "tenants/"), "/")
			return keys[tenant] // "" falls back to SSEKMSKeyID
		},
	})
	if err != nil {
		return err
	}
	for _, tenant := range []string{"acme", "globex"} {
		scoped, err := disk.Scope(tenant, "tenants/"+tenant)
		if err != nil {
			return err
		}
		if _, err := scoped.WriteBytes(ctx, "logo.txt", []byte(tenant), filesystem.WriteOptions{}); err != nil {
			return err
		}
	}
	if _, err := disk.WriteBytes(ctx, "shared/terms.txt", []byte("terms"), filesystem.WriteOptions{}); err != nil {
		return err
	}
	for _, path := range []string{"/app-files/tenants/acme/logo.txt", "/app-files/tenants/globex/logo.txt", "/app-files/shared/terms.txt"} {
		h := fake.lastSent(http.MethodPut, path, "PutObject")
		fmt.Fprintf(out, "kms: %s -> %s %s\n", strings.TrimPrefix(path, "/app-files/"), h.Get("X-Amz-Server-Side-Encryption"), h.Get("X-Amz-Server-Side-Encryption-Aws-Kms-Key-Id"))
	}
	return nil
}
```

Check: `kms: tenants/acme/logo.txt -> aws:kms …/acme-key`, `kms: tenants/globex/logo.txt -> aws:kms …/globex-key` and `kms: shared/terms.txt -> aws:kms …/default-key`. The fake ignores the headers, so this shows what reaches S3, not encrypted storage.

- It is called on every request that creates data, the same as `SSEKMSKeyID`: `Write`, `Copy` (the destination's key), `CreateMultipart`, presigned PUTs (signed) and presigned POSTs, whose key is `prefix/${filename}`, so decide by prefix. It runs on every write, so keep it a map lookup, not a database call.
- One write can name its own key with `RequestOptions.SSEKMSKeyID` (step 14), which wins over both.
- The rules are those of `SSEKMSKeyID`: a KMS or empty `ServerSideEncryption` (an empty one becomes `aws:kms` for objects that get a key), never `AES256` or `SSECustomerKey`; `New` refuses the resolver with either, and a per-call key on such a disk is `CodeInvalidArgument` before anything is sent.
- Reads need no key: S3 records which key encrypted each object. Moving a tenant to a new key changes only new writes; the role needs `kms:Decrypt` on the old key for as long as old objects exist.
- Each tenant's key policy should allow only the application's role, and the tests check only that the right key ID reaches each request; that a key policy really keeps one tenant's objects from another needs a real AWS account and is not proven here.

## 4. Credentials

Credentials never appear in the DSN, so a DSN can be logged. Without credential parameters, the opener takes them from the AWS SDK's default chain, in its order:

1. Environment: `AWS_ACCESS_KEY_ID`, `AWS_SECRET_ACCESS_KEY`, and `AWS_SESSION_TOKEN` for temporary credentials.
2. Shared files: `~/.aws/credentials` and `~/.aws/config`, with `AWS_PROFILE` choosing the profile (SSO profiles included).
3. Web identity (`AWS_WEB_IDENTITY_TOKEN_FILE` and `AWS_ROLE_ARN`), which is how EKS service accounts get a role.
4. The container (ECS) or instance (EC2) role.

For a non-AWS provider with one disk, set `AWS_ACCESS_KEY_ID` and `AWS_SECRET_ACCESS_KEY` to that provider's key pair.

When two disks need different credentials (an R2 bucket and an AWS bucket in one process, or one account per tenant), give each DSN its own. Either name a profile of the shared files:

```text
s3://archive?region=eu-west-1&profile=archive-writer
```

or name the environment variables that hold a key pair, and the opener reads them once, at open time:

```text
s3://media?region=auto&endpoint=https://<account>.r2.cloudflarestorage.com&access_key_env=R2_ACCESS_KEY_ID&secret_key_env=R2_SECRET_ACCESS_KEY
```

`session_token_env` adds a session token for temporary keys. A profile can itself assume a role or use SSO, so `profile` covers those too; the two forms are exclusive. Rotating keys read from variables means reopening the disk; a profile backed by a role or SSO refreshes on its own. Keys read this way are held behind a pointer and format as a placeholder, so logging the client, its options or the disk with `%v` or `%+v` does not print them (the SDK's own cache, used for the default chain and profiles, is the SDK's business: do not log `Options().Credentials`).

To go further (a custom provider, an assume-role chain built in code), build each `*s3.Client` yourself and use `New` instead of the opener.

### Bring your own bucket: a role in the customer's account

Some customers want their files in their own S3 bucket (the model of Segment, Fivetran and Retool). The customer never hands over keys: they create an IAM role in their account that trusts the application's AWS account, on condition of an external ID the application generated for them, and allow that role on their bucket. The application assumes the role with its own credentials, and its disk for that tenant works through the role:

```text
s3://acme-files?region=us-east-1&role_arn=arn:aws:iam::444455556666:role/app-storage&external_id=ext-7f3c9a&role_session_name=tenant-acme
```

or in code, which is the same thing:

```go
client, err := s3.NewRoleClient(ctx, appCfg, s3.RoleOptions{RoleARN: t.RoleARN, ExternalID: t.ExternalID, SessionName: "tenant-" + t.ID})
drv, err := s3.New(s3.Config{Client: client, Bucket: t.Bucket})
disk, err := filesystem.NewDisk("tenant-"+t.ID, drv)
manager.Add(disk) // one disk per tenant
```

- The DSN's other credential parameters (or the default chain) are the application's own and are used only to call `sts:AssumeRole`; every S3 request is signed with the role's temporary credentials. Opening assumes the role once, so a wrong ARN, external ID or trust policy fails at start-up with `CodePermission`, not on the first write.
- The credentials are kept and renewed a minute before they expire (`aws.CredentialsCache` over the SDK's assume-role provider), so the disk works for as long as the process runs. `role_duration` (`RoleOptions.Duration`, default one hour, 15m to 12h and within the role's own maximum) only bounds how long a leaked set stays usable.
- The external ID is required. Without it the role trusts the application's whole account, so another customer could type this customer's role ARN into the application and have it read the bucket for them (the confused-deputy problem). Generate it per tenant on the application's side, store it with the tenant, and never let a tenant choose it. AWS does not treat it as a secret, so the DSN may carry it, but it never appears in an error, and the provider prints only the role and the session name under every `fmt` verb (`%v`, `%+v`, `%#v`), also inside the client's options.
- `s3.RoleCredentials(stsClient, opts)` returns just the renewing `aws.CredentialsProvider`, for building a client by hand; `RoleOptions.Client` swaps in another STS client (a test fake, another region).
- One role can serve every tenant, narrowed per session. `RoleOptions.Policy` is an inline session policy (the session gets only what both the role and the policy allow), `PolicyARNs` managed ones, `Tags` (with `TransitiveTagKeys`) session tags that bucket and key policies match as `aws:PrincipalTag/<key>`, and `SourceIdentity` a name recorded in the customer's CloudTrail for the session and every role it chains to. Tags need `sts:TagSession` and a source identity `sts:SetSourceIdentity` in the role's trust policy:

```go
client, err := s3.NewRoleClient(ctx, appCfg, s3.RoleOptions{
	RoleARN: t.RoleARN, ExternalID: t.ExternalID, SessionName: "tenant-" + t.ID,
	Policy: `{"Version":"2012-10-17","Statement":[{"Effect":"Allow","Action":["s3:GetObject","s3:PutObject"],"Resource":"arn:aws:s3:::shared-bucket/` + t.ID + `/*"}]}`,
	Tags:   map[string]string{"tenant": t.ID},
})
```

- Pin the bucket's owner with `Config.ExpectedBucketOwner` (`expected_bucket_owner=`), the customer's 12-digit account ID: every request then carries `x-amz-expected-bucket-owner`, so if the customer deletes the bucket and someone else in another account creates one with the same name, S3 refuses the calls instead of writing the tenant's files there. A requester-pays bucket needs `Config.RequestPayer: types.RequestPayerRequester` (`request_payer=requester`) on every request instead. Both are signed into presigned URLs too (SigV4 carries them in the URL's query), so a link handed out works only against the bucket they describe.
- The customer's role needs a trust policy naming the application's account with `"Condition": {"StringEquals": {"sts:ExternalId": "<their external ID>"}}`, the bucket permissions below, and `kms:GenerateDataKey`/`kms:Decrypt` when their bucket encrypts with their own KMS key. The application's own identity needs `sts:AssumeRole` on the customers' roles.
- The tests run against an STS fake and an S3 fake: they prove the external ID, session name and duration reach STS, that every S3 request carries the role's key and session token, renewal, and the redaction. A role in a real second AWS account has not been exercised here.

## 5. Visibility: bucket policy or object ACLs

S3 has two ways to make an object public, and the driver uses the one you declare.

**Bucket policy (the default, `VisibilityNone`).** The driver sends no ACL. Who can read is decided by the bucket's policy, and the disk does not declare `SetVisibility`. Every write uses the disk's default visibility, and a write that asks for another one is `CodeUnsupported` rather than silently stored with the wrong access. This is correct for AWS buckets with "bucket owner enforced" object ownership (the AWS default since 2023), and for R2, B2 and most self-hosted stores.

To serve public files, use two buckets: a public one (bucket policy allows `s3:GetObject` for everyone, or a CDN in front of it) opened with `visibility=public&public_url=https://cdn.example.com`, and a private one. See [public and private files](../concepts/public-and-private.md).

**Object ACLs (`acl=true`, `VisibilityACL`).** For AWS buckets whose object ownership still allows ACLs. Each write sends `public-read` or `private` (`Config.PrivateACL` names another non-public canned ACL for private objects, such as `s3.CannedBucketOwnerFullControl` when this disk writes into a bucket another account owns, so that owner can read what it receives), `SetVisibility` calls `PutObjectAcl`, and `Stat` reads the ACL to report `Visibility` (one extra request per `Stat`). A copy carries the source's visibility over, because S3 does not copy ACLs. On a bucket with ACLs disabled, AWS rejects these requests, so do not set `acl=true` there.

**Visibility on direct uploads.** A presigned PUT or POST form sends no ACL unless it is asked to, so it gets the bucket's default (private). In ACL mode the disk declares `PresignVisibility`: `PresignOptions.Visibility` signs `x-amz-acl` into the PUT (`public-read`, or `private` / `Config.PrivateACL`), which the client must send from `SignedRequest.Header` and cannot change, and `PostPolicy.Visibility` pins an `acl` form field and policy condition. Not declared with `UnverifiedSignedHeaders`, since such a store would let a client send another ACL, nor without `acl=true`, where a visibility is `CodeUnsupported` rather than an upload AWS rejects. For browser tickets, `upload.Policy.AllowPublic` decides whether a client may ask for public ([Uploads](../concepts/uploads.md#public-direct-uploads)):

```go
put, err := disk.SignedURL(ctx, "avatars/u7.png", filesystem.PresignOptions{
	Method:      filesystem.MethodPut,
	Expires:     5 * time.Minute,
	ContentType: "image/png",
	Visibility:  filesystem.VisibilityPublic, // signed as x-amz-acl: public-read
})
```

### Checksums S3 verifies

`WriteOptions.SHA256` (a hex SHA-256 the body must have) is checked by the Disk on every backend. S3 checks it too, on its side of the wire (`ChecksumSHA256` capability):

```go
_, err := disk.Write(ctx, "invoices/42.pdf", body, filesystem.WriteOptions{SHA256: sum, SizeHint: size})
```

- With a known size (`SizeHint`, up to 5 GiB) the write is one `PutObject` whose SigV4 payload hash is that digest (`x-amz-content-sha256`, so the body is not read twice to hash it) and which carries `x-amz-checksum-sha256`. S3 refuses a body that does not match, and stores the checksum with the object.
- Without a size, or over 5 GiB, the write goes through the transfer manager as a multipart upload, whose S3 checksums are per part; the whole-object digest is then checked by the Disk alone.
- Checked on 2026-10-06 against SeaweedFS and RustFS (`TestChecksumAgainstARealStore`): a body that does not match the digest is refused and nothing is stored.

- Part numbers run from 1 to 10,000. Every part but the last must be at least 5 MiB; S3 rejects a smaller one at completion (`EntityTooSmall`, mapped to `CodeInvalidArgument`).
- `UploadPart` (through your server) needs the part's exact size, because S3 needs a content length for a body it cannot seek.
- `PresignPart` signs a PUT for one part; the client sends it and S3 returns the part's ETag in the response. `ListParts` follows S3's pagination and returns every part, so the server does not need to trust ETags reported by the client.
- `IfNotExists` on `Write` is checked by S3 when the PUT (or the completion of the transfer manager's multipart upload) commits, so a losing writer uploads its whole body before getting `CodeExists`.
- `CreateMultipart` with `IfNotExists` is `CodeUnsupported`: S3 checks the condition at completion, where the driver no longer has the options, and completing unconditionally would overwrite. `Write` honours `IfNotExists` for bodies of any size.
- `AbortMultipart` of an unknown upload succeeds.
- An upload that is never completed or aborted keeps its parts, and AWS bills them, until something aborts it. Add a lifecycle rule with `AbortIncompleteMultipartUpload` to the bucket.
- Where the store has no lifecycle rules (or you cannot set them), open the disk with `sweep_uploads=true` and call `disk.SweepAbandoned(ctx, time.Now().Add(-24*time.Hour))` on a schedule: it lists the bucket's unfinished multipart uploads (`ListMultipartUploads`) and aborts those initiated before the cutoff, returning how many. S3 records when an upload started, not its last part, so pick a cutoff beyond your longest upload. The sweep is bucket-wide: it also aborts uploads another application started in the same bucket, and it needs `s3:ListBucketMultipartUploads` and `s3:AbortMultipartUpload`. It is off by default because the lifecycle rule does the same work on the server, for free. Checked on 2026-10-06 against SeaweedFS and RustFS (`TestSweepUploadsAgainstARealStore`). A disk with a `prefix` never sweeps: sweep the unprefixed disk. `disk.FindAbandoned(ctx, cutoff)` is the dry run: the same listing, returning each upload's ID, key and initiation time, aborting nothing.

`upload.Uppy` speaks the protocol of Uppy's AWS S3 plugin on top of exactly these calls; it needs `Multipart` and `PresignPart`, which among the built-in drivers only S3 declares.

## 9. Listing, deleting, copying

- `List` uses `ListObjectsV2`; the cursor is S3's continuation token, opaque to callers. A page holds at most 1,000 entries (`filesystem.DefaultPageSize`, S3's maximum), so one page is one request.
- Keys ending in `/` are directory markers some tools create; keys in this library never end in `/`, so markers are not listed.
- `DeleteKeys` sends `DeleteObjects` with up to 1,000 keys per request. Keys S3 refuses come back in a `*filesystem.BatchError` with a code per key (`AccessDenied` is `CodePermission`, `SlowDown` and `InternalError` are `CodeUnavailable`); every other key is deleted. When a whole request fails, its keys and every later key are reported, since earlier requests did delete theirs.
- `DeletePrefix` lists and deletes in batches of 1,000 and stops at the first batch with failures, returning them as a `*filesystem.BatchError`. The Disk refuses `DeletePrefix` of the root.
- `Copy` is `CopyObject`, which keeps metadata and content type. S3 limits a single copy to 5 GiB; a larger object fails with the provider's error.
- `Move` is Copy then Delete, so it is not atomic: a failure between the two leaves both keys.

## 10. Errors

S3 errors are mapped to `filesystem` codes; the SDK's error stays reachable with `errors.As`.

| S3 error or status | Code |
|---|---|
| `NoSuchKey`, `NotFound`, `NoSuchUpload`, 404 | `CodeNotFound` |
| `PreconditionFailed`, 412 | `CodeExists` |
| `AccessDenied`, 403 | `CodePermission` |
| `InvalidPart`, `InvalidPartOrder`, `EntityTooSmall`, `InvalidStorageClass`, `BadDigest` and the checksum mismatches | `CodeInvalidArgument` |
| `InvalidObjectState` (a read of an archived object not yet restored) | `CodeConflict`, with `s3.ErrArchived` in the chain (`errors.Is`), as the Azure driver answers for its archive tier; `layer.Retry` never retries it, since retrying cannot help |
| 405 on `ReadVersion` or `RestoreVersion` (a delete marker) | `CodeNotFound` |
| `SlowDown`, 429, 5xx | `CodeUnavailable`, carrying the response's `Retry-After` when it sent one, so `layer.Retry` waits at least that long and `fshttp` passes it on |
| anything else | `CodeUnknown` |

A ranged read starting past the end of an object returns an empty body, not `InvalidRange`, after confirming the object exists. The SDK retries throttling and 5xx itself; `layer.Retry` adds a retry around the whole operation. See [errors](../concepts/errors.md).

## 13. CORS for browser uploads

A browser that uploads or downloads directly with a signed URL, a presigned part or a presigned POST calls the bucket from your site's origin, so the bucket must allow that origin (CORS). `s3.SetCORS` sets the bucket's rules, and `s3.DirectUploadCORS` is the recommended rule:

```go
client, _ := filesystem.As[*s3.Client](disk)
err := fss3.SetCORS(ctx, client, "acme-media", fss3.DirectUploadCORS("https://app.example.com"))
```

- The recommended rule allows `GET`, `HEAD`, `PUT` and `POST` from the origins you name; the request headers a signed request may carry (`Content-Type`, the pinned `Cache-Control`, `Content-Disposition` and `Content-Encoding`, and `x-amz-*` for encryption and checksums); exposes `ETag`, which Uppy's multipart uploader reads; and lets browsers cache the preflight for an hour. Name your origins: `*` lets any site use links your users hold.
- `SetCORS` replaces the bucket's whole CORS configuration (`PutBucketCors`). Pass every rule you want in one call; add your own `s3.CORSRule` values next to the recommended one.
- It is a setup step, not part of the Disk: run it from a deploy script or once at start-up, with credentials allowed `s3:PutBucketCORS`. The application's runtime credentials need not (and should not) have that permission.
- Checked on 2026-10-06 against SeaweedFS and RustFS: after `SetCORS`, a preflight for a signed PUT is allowed from the configured origin and not from another (`TestCORSAgainstARealStore`).

## 14. Object features: tags, holds, versions, classes, archives, SSE-C, checksums

Each is declared by configuration, never assumed, because providers differ (R2 has no object tags; self-hosted stores keep no storage classes). The portable calls are the Disk's own (`Tags`, `SetHold`, `Versions`, `ReadVersion`, `SetStorageClass`, `Restore`); what `WriteOptions` has no field for rides on the context with `s3.WithRequestOptions(ctx, disk, key, opts)`, so it still goes through the Disk's key cleaning, a scoped disk's prefix and the interceptors. The options are bound to that exact key: another write made with the same context (a staging file, a thumbnail, the same name in another directory) does not get them, so a reused context never spreads a legal hold or a retention. The helper takes the disk and resolves the key itself (`disk.DriverKey`: cleaned, under a scoped disk's prefix), so a caller never joins prefixes and cannot bind the options to the wrong key; an invalid key is its error. Use the returned context with the same disk. They are not consumed, so a retried call gets them again.

```go
cfg := fss3.Config{Client: client, Bucket: "records", Tagging: true, ObjectLock: true, ObjectLockDays: 30, Versioning: true}
drv, _ := fss3.New(cfg)
if err := drv.CheckBucket(ctx); err != nil { // the bucket really has Object Lock and versioning
	return err
}
disk, _ := filesystem.NewDisk("records", drv)

// Tags and a legal hold set with the write itself.
wctx, err := fss3.WithRequestOptions(ctx, disk, "contracts/acme.pdf", fss3.RequestOptions{Tags: map[string]string{"case": "4711"}, LegalHold: true})
if err != nil {
	return err // an invalid key
}
_, err = disk.WriteBytes(wctx, "contracts/acme.pdf", pdf, filesystem.WriteOptions{})

err = disk.Delete(ctx, "contracts/acme.pdf")                   // CodePermission: held
_, err = disk.WriteBytes(ctx, "contracts/acme.pdf", other, filesystem.WriteOptions{}) // CodePermission too
err = disk.SetHold(ctx, "contracts/acme.pdf", filesystem.Hold{}) // lift the legal hold
vs, _ := disk.Versions(ctx, "contracts/acme.pdf")               // newest first
err = disk.RestoreVersion(ctx, "contracts/acme.pdf", vs[1].ID)   // undo the last overwrite
```

- **Tags** (`Tagging`, `tagging=true`): `Disk.Tags` and `SetTags` (an empty map deletes them all), and `RequestOptions.Tags` on a write or copy. A copy keeps the source's tags unless the request names new ones.
- **Legal holds and retention** (`ObjectLock`, `object_lock=true`): the bucket must have been created with Object Lock. `SetHold` sets the legal hold and the retention date in `ObjectLockMode` (`GOVERNANCE` by default, which `s3:BypassGovernanceRetention` can lift; `COMPLIANCE` is WORM and nobody can shorten it); a zero `Hold` lifts both. `ObjectLockDays` gives every write a retention; `RequestOptions.LegalHold` and `RetainUntil` set one per write. Every retention is capped by `MaxRetention` (`max_retention_days`, default `DefaultMaxRetention`, ten years): a later date is `CodeInvalidArgument`, so a mistaken date cannot become a COMPLIANCE lock nobody can lift. A held object refuses with `CodePermission` everything that would remove it or make a new, unprotected version current, matching GCS and Azure: `Delete`, `DeleteKeys` and `DeletePrefix`, `Write`, `Copy` and `Move` onto it, `SetStorageClass`, `RestoreVersion`, and a multipart upload (at creation and again at completion). S3 itself would accept those, hiding the held version behind a delete marker or a newer version. Each check is one HEAD; `DeleteKeys` and `DeletePrefix` run 16 at a time.
- **Versions** (`Versioning`, `versioning=true`): `Versions` lists every version and delete marker, newest first; `ReadVersion` reads one; `RestoreVersion` copies one onto the key as a new latest version, which also undoes a delete. On a versioned bucket `Stat` reports the version under `s3.MetaVersionID`.
- **Storage classes** (`StorageClasses`, `storage_classes=true`): `StorageClass` is the class of every write, `RequestOptions.StorageClass` one write's; `Disk.SetStorageClass` copies the object onto itself in another class; `Stat` reports `Entry.StorageClass` (empty for STANDARD on AWS, which omits it).
- **Archives** (`Restore`, `restore=true`): a read of an object in `GLACIER` or `DEEP_ARCHIVE` fails with `CodeConflict` and `s3.ErrArchived` until `Disk.Restore(ctx, key, filesystem.RestoreOptions{Days: 7})` has finished, at `RestoreTier` or `RequestOptions.RestoreTier`. A second `Restore` while one runs succeeds. `Stat` reports `s3.MetaRestore` (`ongoing` or `restored`) and `s3.MetaRestoreExpiry`.
- **Customer-provided keys** (`SSECustomerKey`, `sse_c_key_env=VAR`): `s3.NewCustomerKey(key32)` holds the 256-bit key, which goes on every write, read, copy (as source and destination), multipart part and presigned request; S3 never stores it, so losing it loses the objects. It is exclusive with `sse` and `sse_kms_key_id`, and the disk does not declare `PresignPost`, whose form fields would hand the key to the browser. A signed request must carry the key, and the key decrypts every object of the disk, so an SSE-C disk declares no `Presign`, `PresignPart` or `PresignHeaders` unless `PresignCustomerKey` (`presign_customer_key=true`) opts in; with it, each `SignedRequest.Header` holds the key, so hand such URLs only to clients as trusted as the application, never to browsers. `PresignPost` stays off either way. A `CustomerKey` formats as a placeholder with every verb, inside a `Config` or a `Driver` too, and the DSN only names the variable that holds it.
- **Per-write KMS key** (`RequestOptions.SSEKMSKeyID`): the KMS key of one write, copy, multipart upload or presigned PUT/POST, overriding `SSEKMSKeyFor` and `SSEKMSKeyID` (see "One KMS key per tenant on a shared disk", step 3). Refused with `CodeInvalidArgument` on an SSE-S3 or SSE-C disk.
- **Checksums** (`ChecksumAlgorithm`, `checksum=CRC32C`): S3 stores and verifies a checksum of that algorithm on every write and copy (`RequestOptions.ChecksumAlgorithm` for one); `Stat` then reports it under `s3.MetaChecksumPrefix` plus the algorithm (`s3:checksum-crc32c`, base64). A body that does not match is `CodeInvalidArgument`. With an algorithm other than SHA-256 the disk does not declare `ChecksumSHA256`, since S3 keeps one checksum per object; the Disk still checks `WriteOptions.SHA256` itself.

## 15. Bucket setup: lifecycle, replication, object ACLs, scoped credentials

These are adapter functions built from typed structs, like `SetCORS`: setup steps run with admin credentials, not Disk capabilities. Each has a reader, so a deploy script can check what is in place.

```go
// Expire temporary files after a day, clean up abandoned multipart uploads, archive logs.
err := s3.SetLifecycle(ctx, client, "acme-media",
	s3.LifecycleRule{ID: "tmp", Prefix: "tmp/", ExpireAfterDays: 1},
	s3.LifecycleRule{ID: "uploads", AbortIncompleteUploadsAfterDays: 7},
	s3.LifecycleRule{ID: "logs", Prefix: "logs/", Transitions: []s3.LifecycleTransition{{AfterDays: 90, StorageClass: "GLACIER"}}},
)
rules, err := s3.Lifecycle(ctx, client, "acme-media")
```

- `SetLifecycle` replaces the whole lifecycle configuration; `Lifecycle` reads it back (nil when the bucket has none). Prefixes are bucket prefixes: a disk scoped to `tenant` stores its keys under `tenant/`. `Disabled` keeps a rule without applying it.
- A stored rule using anything `LifecycleRule` cannot represent (a tag or size filter, dates, noncurrent-version actions, delete-marker cleanup) makes `Lifecycle` fail with `CodeUnsupported` naming the rule, rather than return it with that part dropped: written back, a tag-filtered "expire after a day" without its tag would expire the whole bucket. `Replication` does the same for rules it cannot represent.
- `SetReplication(ctx, client, bucket, s3.ReplicationConfig{Role, Rules})` sets cross-region replication and `Replication` reads it back. S3 requires versioning on the source and every destination, and an IAM role S3 can assume; objects written before the configuration are not copied. `ReplicateDeletes` decides whether the destination is a mirror or a backup.
- `SetObjectACL(ctx, client, bucket, key, s3.ObjectACL{...})` sets a typed canned ACL (`s3.CannedBucketOwnerFullControl` and the others) or explicit grants to canonical users, groups or email addresses; `ObjectGrants` reads them back. Anything that opens the object beyond the account (`CannedPublicRead`, `CannedPublicReadWrite`, `CannedAuthenticatedRead`, a grant to `GroupAllUsers` or `GroupAuthenticatedUsers`) is refused unless `AllowPublic` is set. `key` is the bucket key: pass `disk.DriverKey(key)`, and a key that is not already clean is refused. Buckets with Object Ownership set to "bucket owner enforced", the default since 2023, refuse ACLs.
- `DelegatePrefix(ctx, sts.NewFromConfig(cfg), s3.DelegateOptions{Role, SessionName, Bucket, Prefix, Write, Duration})` assumes a role with a session policy (`PrefixPolicy`) that allows only `bucket/prefix/*` and listings under `prefix/`, and returns `ScopedCredentials` with their expiry, for a client that uploads to its own folder directly. Prefixes containing IAM wildcards (`*`, `?`, `${…}`) are refused, so the policy is never wider than the folder. The credentials print with the secret and token redacted; `Provider()` turns them into an `aws.CredentialsProvider`.
  - `Partition` is the AWS partition every ARN of the policy names (`arn:<partition>:s3:::…`). Empty means the role ARN's partition, or `s3.PartitionAWS` when `Role` is not an ARN, so a GovCloud role (`arn:aws-us-gov:iam::…`) gets a GovCloud policy without setting anything; `s3.PartitionChina` and `s3.PartitionGovCloud` name the others, and any partition name of lowercase letters, digits and hyphens is accepted. A `Partition` that differs from the role's is `CodeInvalidArgument`, since STS assumes only roles of its own partition. `SessionPolicy(o)` returns the policy for a whole `DelegateOptions`; `PrefixPolicy(bucket, prefix, write)` is the same in the `aws` partition with no KMS keys.
  - `KMSKeyARNs` lists the customer-managed KMS keys of an SSE-KMS bucket. A session policy intersects with the role's, so without it the credentials cannot read or write objects encrypted with those keys even when the role may. One extra statement allows `kms:Decrypt` on exactly those keys, plus `kms:GenerateDataKey` when `Write` is set. Each entry must be a key ARN (`arn:<partition>:kms:<region>:<account>:key/<id>`) in the delegation's partition, without wildcards; an alias ARN is refused, because IAM authorizes these calls on the key. Empty adds no statement, as before.
- `PresignOptions.AllowedIP` is not supported by S3 presigned URLs: `SignedURL` answers `CodeUnsupported`. Restrict by address with a bucket policy (`aws:SourceIp`) instead.

```go
	SessionName: "user-42",
	Bucket:      "media",
	Prefix:      "users/42",
	Write:       true,
	Duration:    time.Hour,
	KMSKeyARNs:  []string{"arn:aws-us-gov:kms:us-gov-west-1:111122223333:key/1234abcd-12ab-34cd-56ef-1234567890ab"},
})
```

The session policy then allows `arn:aws-us-gov:s3:::media/users/42/*`, listings under `users/42/`, and `kms:Decrypt` and `kms:GenerateDataKey` on that one key.

## Pitfalls

- **`acl=true` on a bucket without ACLs.** AWS refuses ACL requests on buckets with "bucket owner enforced" ownership, so every write fails. Leave `acl` off and use a bucket policy.
- **`conditional_write=true` on a provider that ignores `If-None-Match`.** `IfNotExists` would become a silent overwrite. Turn it on only for providers you have checked (AWS since 2024, SeaweedFS in `task test:s3`).
- **Forgetting the CORS rule** for browser uploads: the PUT reaches S3 but the browser cannot read the response or the ETag.
- **SeaweedFS and other filer-backed stores** keep an empty "directory" after its last object is deleted and list it. Use `prune_prefixes=true` there.
- **`COMPLIANCE` retention is permanent.** Nobody, not even the account root, can shorten or remove it before it expires; try `GOVERNANCE` first.
- **`presign_customer_key=true` hands out the key.** Every signed URL of an SSE-C disk carries the key that decrypts all of its objects.
- **SSE-C keys are not recoverable.** S3 keeps only a hash; store the key in your secret manager before the first write.
- **Abandoned multipart uploads** are billed until aborted; add a lifecycle rule, or, where there is none, `sweep_uploads=true` and a scheduled `SweepAbandoned`.
