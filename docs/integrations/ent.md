# ent

You will read the records tables (`fs_files`, `fs_attachments`) with the client [ent](https://entgo.io) generates for your app: typed queries, `WithAttachments` and `WithFile` eager loading, and edges from your own entities to files. The module is `github.com/ubgo/filesystem/contrib/ent` (package `fsent`). It gives two mixins, `FileMixin` and `AttachmentMixin`, that carry each table's name, every column with the Store's names and types, and a hook that refuses writes, plus the two edges between them.

Read this page if your app's data layer is generated by ent and you want files in it. Writes still go through the Store.

## Before you start

- A Store, as in [Files](../records/files.md), migrated with `Store.Migrate`.
- ent in your app (`go run entgo.io/ent/cmd/ent new` or an existing `ent/schema` directory). The module requires `entgo.io/ent` and no SQL driver (`deps_test.go` enforces it).
- Install: `go get github.com/ubgo/filesystem/contrib/ent`.

## Read only, on purpose

Every write goes through `records.Store`: it runs plugin hooks (quota, versions, folders), emits the events the audit log and your webhooks hear, and keeps a stored object consistent with its row. Both mixins install an ent hook that fails every mutation (create, update, delete) with `fsent.ErrReadOnly` (`permission`), so a generated `Create` or `Delete` cannot write behind the Store's back. Import your generated `ent/runtime` package (ent requires it for mixin hooks); without it the hook is not registered. And never run the generated `client.Schema.Create` against the database that holds these tables: they belong to `Store.Migrate`.

`File` reads `fs_files` and `Attachment` reads `fs_attachments`; the edge names are `fsent.EdgeAttachments` and `fsent.EdgeFile`, so the generated client has `QueryAttachments`, `QueryFile`, `WithAttachments` and `WithFile`. The ID of each is the Store's string ID. The schemas may have other names, and your own schemas may add edges to them (a `Post` with an edge to `Attachment` through `owner_id`, for example).

A Store built with `records.WithTablePrefix` or `records.WithTableNames` (see [Migrations: Step 6 — Other table names](../records/migrations.md#step-6--other-table-names)) keeps its tables and indexes under other names. Give both mixins the same mapping in `Names`, a `records.TableNamer`, and they name the tables and indexes the Store created; the zero value keeps the default `fs_` names:

```go
// names is the mapping the Store was built with: WithTablePrefix("app_") prefixes every name.
var names records.TableNamer = func(name string) string { return "app_" + name }

func (File) Mixin() []ent.Mixin       { return []ent.Mixin{fsent.FileMixin{Names: names}} }
func (Attachment) Mixin() []ent.Mixin { return []ent.Mixin{fsent.AttachmentMixin{Names: names}} }
```

## Step 2 — Generate and read

Run ent's generator as usual. Pin it in `go.mod` with `go get -tool entgo.io/ent/cmd/ent@v0.14.6` and run `go tool ent generate ./ent/schema`; with ent v0.14.6 on Go 1.26 also require a current `golang.org/x/tools` (`go get golang.org/x/tools@latest`), since the one ent itself requires fails with `internal error: package "context" without types`. Then open the client on the Store's database (`entsql.OpenDB(dialect.Postgres, db)` with the same `*sql.DB`), and query. The module's test program, [`testdata/entcheck/main.go`](../../contrib/ent/testdata/entcheck/main.go), lists a scope's live files newest first with `client.File.Query().Where(file.Scope("t"), file.DeletedAtIsNil()).Order(ent.Desc(file.FieldCreatedAt), ent.Desc(file.FieldID)).WithAttachments()`, then a post's gallery in position order with `client.Attachment.Query()…WithFile()`, then tries `client.File.Delete()`, which the mixins' hook refuses with `fsent.ErrReadOnly`. It imports the generated `ent/runtime` package so the hook is registered.

Filter by `Scope` first in every query, as the Store does, or a listing crosses tenants; filter `DeletedAtIsNil()` to leave trashed files out, as `Store.Files` does. `metadata` is the JSON object `records.File.Metadata` is stored as.

## Step 3 — Query and eager-load

[`examples/integrations-orm`](../../examples/integrations-orm/README.md) carries a client generated from the two schemas above (`ent/`, generated with the module's pinned `go tool ent generate`; the schemas are in `ent/schema/schema.go`). A Store writes the rows: `cover.txt`, `draft.txt` and `map.txt` attached to post `p1`'s gallery, `draft.txt` then trashed. The gallery query filters by scope first, owner and role, and keeps only attachments whose file is live with `HasFileWith(file.DeletedAtIsNil())`, as `Store.Attachments` does:

<!-- ds:block id=entgallery-2fun6t4a -->
**entGallery** · [`examples/integrations-orm/ent.go:31-41`](../../examples/integrations-orm/ent.go#L31-L41)

```go
func entGallery(ctx context.Context, client *ent.Client, scope, owner string) ([]*ent.Attachment, error) {
	return client.Attachment.Query().
		Where(
			attachment.Scope(scope),
			attachment.OwnerType(ownerPost), attachment.OwnerID(owner), attachment.Role(roleGallery),
			attachment.HasFileWith(file.DeletedAtIsNil()),
		).
		Order(ent.Asc(attachment.FieldPosition), ent.Asc(attachment.FieldID)).
		WithFile().
		All(ctx)
}
```
<!-- /ds:block hash=819074 -->

The program opens the client on the Store's own `*sql.DB` (`ent.NewClient(ent.Driver(entsql.OpenDB(dialect.SQLite, db)))`), imports the generated `ent/runtime` package so the read-only hooks are registered, prints the gallery, and then tries a generated delete:

<!-- ds:block id=readwithent-qkkbw8hc -->
**readWithEnt** · [`examples/integrations-orm/ent.go:46-63`](../../examples/integrations-orm/ent.go#L46-L63)

```go
func readWithEnt(ctx context.Context, out io.Writer, db *sql.DB) error {
	client := openEnt(db)
	gallery, err := entGallery(ctx, client, tenant, postID)
	if err != nil {
		return err
	}
	for _, a := range gallery {
		fmt.Fprintf(out, "ent gallery: %d %s %d bytes\n", a.Position, a.Edges.File.Filename, a.Edges.File.Size)
	}
	_, err = client.File.Delete().Where(file.Scope(tenant)).Exec(ctx)
	fmt.Fprintf(out, "ent delete refused: %t\n", errors.Is(err, fsent.ErrReadOnly))
	n, err := client.File.Query().Where(file.Scope(tenant)).Count(ctx)
	if err != nil {
		return err
	}
	fmt.Fprintf(out, "ent rows after the refused delete: %d\n", n)
	return nil
}
```

The delete fails with `fsent.ErrReadOnly` before any statement runs, so all three rows, the trashed one included, are still there.

## How it is kept true

- `TestFieldsMatchTables` compares every mixin field and index with the columns and indexes `Store.Migrate` creates, on SQLite and, with `task test:engines`, on Postgres and MySQL. A column or index a records migration adds fails it until the mixin has it. `TestNamesFollowTheStore` checks mixins given `Names` against a Store built with `records.WithTablePrefix` the same way.
- `TestGenerateBuildAndRead` is the build-is-the-test proof: it copies the schemas and the program above to a temporary module, runs ent's code generator on them (`go tool ent generate`, the version pinned in the module's `go.mod`), builds and runs the program against a SQLite database the Store wrote, and compares its output with `Store.Files` and `Store.Attachments`. It also checks that the delete is refused. A field, edge or annotation ent rejects fails here; it caught an edge declared immutable over a mutable field while the module was written. It never skips for want of an installed tool; it skips only when go cannot download the generator, and says so.

## What can go wrong

- `fsent: the records tables are written only through records.Store` — a generated mutation ran; write through the Store instead.
- A mutation succeeds — your program does not import the generated `ent/runtime` package, so the mixins' hooks were never registered.
- `no such table: fs_files` (or `relation "fs_files" does not exist`) — the Store was built with a table prefix or mapping and the mixins were not; give them the same mapping in `Names` and regenerate.
- ent's migration wants to change `fs_` tables — `client.Schema.Create` was run on the Store's database; let `Store.Migrate` own them.
- **`WithFile()` loads trashed files.** Eager loading ignores trash; filter the attachment query with `HasFileWith(file.DeletedAtIsNil())` (Step 3), or drop attachments whose `Edges.File.DeletedAt` is set.
- **The generated client is a snapshot.** When a records migration adds a column, upgrade `contrib/ent` (its mixin gains the field) and regenerate; a client generated from an older mixin simply does not see the new column.
- Plugin tables (`fs_audit`, `fs_file_versions`, `fs_quota_usage`, …) have no mixin; read them through their plugins' Go API.
